# 05 复盘：最难的问题、收获和下一步

## 最难搞的问题

### 1. 既要离线跑，又不能把逻辑写死

题目要求能离线 Mock，但又强调条件分支、自动重试、固定日志这些不能算 ReAct。如果 Mock 只是死板地回放录好的轨迹，换了文档答案都不变，那真就是在评审面前演戏了。

最后的做法是把两件事彻底切开：

- **决策全留给模型**：循环代码里不写任何“下一步干嘛”的分支逻辑，工具报错也只是当成 Observation 填回给模型，绝不自动重试。
- **Mock 做成启发式策略**：它不调大模型，但和真实模型走同一个接口、看同样的消息。修改文档后 Mock 的答案会跟着变，这一点用 `test_editing_a_document_changes_the_answer` 跑通了测试。文档里我也写明了它的边界：它只保流程能跑通，不证明决策质量。

### 2. 冲突判断到底靠模型还是靠代码？

刚开始我想让代码去自动识别文本冲突，后来发现根本搞不定。“两段话是不是在讲同一件事”很难用简单规则判定。比如 D04 里的“每天 100 元”和 D01 里的“5000 元”，虽然都是金额，但压根不是冲突。

最后把分工理顺了：让模型去判断有没有冲突，程序只负责盯紧证据链。只要模型报冲突，必须拉出至少两份文档的原文引用，并给出一个确认问题；另外强制要求模型调用 `read_doc` 读全文，免得它只看摘要错过了像 C12 这种适用范围条款。

### 3. 引用校验到底要多严？

如果做纯字面匹配，规则太严了：模型经常把全角括号写成半角，或者随手删掉空格。但完全放开又怕模型把二次加工的句子当成“原文引用”。

最后用了 NFKC 归一化加去空白后再做子串匹配，同时严禁使用省略号拼接。要是被退回了，直接在报错消息里告诉模型具体原因，让它重新摘录。

### 4. 数字校验天天“误伤自己人”

“答案里的数字必须在引用中出现”这条规则，刚开始天天踩雷。最开始误伤了三类数字：文档 ID 里的数字（D01 的 01）、版本日期、用户提问里的数字（“工作满 3 年”的 3）。这三类在设计时就加进白名单放行了。

结果接入真实模型时，模型又甩出来一堆预料之外的格式：段落编号（S2）、列表序号（"2."）。连通性测试时，DeepSeek 因为这个被连续误退回了 2 次，多浪费了 2 步。离线测试根本发现不了这个问题，因为之前 Mock 的答案格式是我自己写的。补上排除规则后，v1 的 12 个真实用例才算顺利过关。

后面又陆陆续续遇到了圆圈序号、条款引用（"第 2 条"）、字面 `\n`、中文数字（“满三年”对“3 年”）这些幺蛾子，在 v2.1–v2.3 慢慢补救。处理中文数字时我没敢全部转换，只换算了带单位的（比如“三年”、“十五天”）。因为冲突回答里模型极喜欢写“两份文档”，要是全部换算会导致大面积误判。每次放宽逻辑前，我都拿历史记录重放一遍，确保真正该拦的依然能拦住。

### 5. 预期结果（Ground Truth）自己居然是错的

C07（“WFH 要先申请什么？”）原本只接受 `answered`。结果 DeepSeek 第一次跑完给出了 `insufficient_evidence`：它确实找到了 VPN 条款，但指出知识库压根没写“WFH 行为本身需不需要提前审批”。我自己回去看了一遍原文，发现模型是对的，是我预设的预期答案有问题。

直接看答案改标准肯定有作弊嫌疑，所以我保留了原始记录，并在评估文档里写清楚了调整过程。v2 做得更彻底：与其放宽预期，不如把“部分可答算什么状态”直接定成规则（决策 1）。规则定下来后，预期重新收紧为 `answered`，后面跑了 3 次都稳定通过。

### 6. 两条单独看合理的规则，凑在一起打架了

v2 的决策 3 要求“引用只放支撑结论的原文”，而原有的数字校验要求“答案里的数字必须在引用中出现”。这两条分开看都没毛病，合在一起就坑了：模型在补充信息里写的价格、天数，因为不是直接结论没放进引用，结果直接被数字校验退回。

在 3 次稳定性测试里，`finish` 被退回的次数直接从 0 飙升到了 10 次。要不是去翻了重试次数等过程指标，光看 100% 的最终通过率，这问题还真就被掩盖过去了。

## 真正的收获

- **提示词和代码校验分工要明确**：模型能决定的写进提示词，程序必须保证的写进校验。“引用必须是原文”写在提示词里只是期望模型做到，写在 `check_finish` 代码里才能真正保证做到。
- **检索工具的弱点反而是测试的好题目**：BM25 搜不到“WFH”，正好拿来测试模型会不会自动改写检索关键词。
- **测试用例要有区分度**：不能全是一样的难度。调整后分成两档，中等强度改写（C02）验证基本一致性，高强度改写（C07）专门验证模型的查询改写能力。
- **真实模型才能检验规则合理性**：数字校验误伤和 C07 预期过窄，全是第一次接入真实 LLM 才暴露的。离线测试只能保证代码按设计跑，规则本身合不合理，得靠真实输出来检验。
- **改规则前一定要拿历史日志做 Replay**：v2.1 剩下的 6 次退回，光看统计汇总只显示“句中序号错误”；调出答案原文逐条看才发现，主要是“第 2 条”这种条款引用，还有模型把换行写成了字面的 `\n`。修之前拿所有退回记录重放了一遍新规则，确认像“0 天”这种真正有问题的不会被放过，才花钱重跑。
- **改进要看数据，结论实话实说**：v2 的 6 个优化点里，“失败 2 次就停”和“追问列出选项”效果立竿见影；“回答精简”改完发现字数也就少了 8%，效果非常有限。

## 下一步计划

1. **把提示词里的软规则变成硬约束**：在代码里限制单轮检索次数，让“最多换 2 次关键词”真正生效（C06 目前仍会多检索一次）。
2. **搞混合检索**：把向量检索和 BM25 结合起来，提高同义词召回率，顺便对比一下两种检索下模型改写 Query 的频率变化。
3. **扩充冲突评估集**：多构造一些“有冲突 / 没冲突 / 带有适用条件”的文档对，定量统计模型判断冲突的准确率和误报率。
4. **跑多模型对比**：拿同一套用例分别去跑 DeepSeek、通义千问和本地小模型，对比步数、被退回次数和最终成功率。
5. **引用加上字符偏移量**：引用结构里带上段落 ID 和字符 offset，方便前端直接做原文高亮。
6. **做 Session 持久化和简易界面**：方便非技术同事直接上手测试和试用。
