# 05 复盘：最难的问题、收获和下一步

> 初稿，建议用自己的话改写，并补上自己的体会。

## 最难的问题

### 1. 离线可运行，又不能把决策写死

题目要求有离线 Mock，同时又说"固定条件分支、自动重试、预设决策日志"不算 ReAct。如果 Mock 只是回放一条预先录好的轨迹，替换文档后它的答案不会变，等于在评审面前演戏。

最后的做法是把两件事分开：

- **决策**只在模型那一侧。循环代码没有任何"下一步做什么"的分支，工具失败也只是作为观察返回，不自动重试。
- **Mock** 是一个读取真实观察结果的启发式策略。它和真实模型走同一个接口、看同样的消息。修改文档后 Mock 的答案会跟着变，这一点有测试覆盖：`test_editing_a_document_changes_the_answer`。文档里也写明了它的边界，它不证明决策质量。

### 2. 冲突能交给程序检测吗？

一开始想让程序自动识别冲突，但"两段话是否在讲同一件事"没法通用地判断。比如 D04 的"每天 100 元"和 D01 的"5000 元"都是金额，却不是冲突。

最后的分工：**冲突由模型判断，程序验证证据是否完整**。报冲突必须引用至少两份文档的原文，并给出确认问题；同时强制模型通过 `read_doc` 读取全文，这样它才有机会看到适用范围条款（C12）。

### 3. 引用校验的严格程度

只做逐字匹配太严：模型常把全角括号写成半角，或者去掉空格。完全放开又会让改写过的"引用"混进来。最后用 NFKC 归一化加去空白后再做子串匹配，并且明确禁止用省略号拼接。被退回时会告诉模型原因，让它重新摘录。

### 4. 数字校验的误伤

"答案里的数字必须出现在引用中"这条规则，一开始会误伤三类数字：文档 ID 里的数字（D01 的 01）、版本日期、用户问题里的数字（"工作满 3 年"的 3）。这三类在设计时就放行了。

但真实模型还用了没预料到的写法：段落编号（S2）和列表序号（"2."）。连通性测试里，DeepSeek 因此被误退回两次，多花了 2 步。离线测试发现不了这个问题，因为假模型的答案格式是我写的。补上排除规则后，v1 的 12 个真实用例中没有再被误退回。

之后又陆续发现了圆圈序号、条款引用（"第 2 条"）、字面 `\n`、中文数字（"满三年"对"3 年"）这几种写法，分别在 v2.1–v2.3 中修正。处理中文数字时，没有把所有汉字数字都换算，只换算带单位的（"三年""十五天"），因为冲突回答里几乎都会写"两份文档"，全部换算会造成大面积误判。每次放宽前都先用历史记录回放，确认该拦的仍然会被拦下。

### 5. 用例预期本身也会出错

C07（"WFH 要先申请什么？"）原本只接受 `answered`。DeepSeek 第一次返回 `insufficient_evidence`：它找到了 VPN 条款，但指出知识库没写 WFH 本身是否要审批。复核后我认为它是对的，错的是预期。

放宽预期有"看答案改标准"的嫌疑，所以保留了原始记录，并在评估文档里写明了调整过程。v2 的做法更彻底：与其放宽预期，不如把"部分可答算什么状态"写成规则（决策 1）。规则定下后，预期重新收紧为 `answered`，3 次运行都稳定通过。

### 6. 两条单独看都合理的规则，合在一起会冲突

v2 的决策 3 要求"引用只放支撑结论的原文"，原有的数字校验要求"答案里的数字必须在引用中"。两条规则单独看都对，合在一起时，模型在补充信息里写的价格、天数就会被退回。3 次稳定性运行中，`finish` 被退回的次数从 0 涨到 10，才暴露出这个问题。只看通过率（仍然 100%）是发现不了的，要看过程指标。

## 收获

- **把模型能决定的和程序必须保证的分开写。** 前者写进提示词，后者写进校验。"引用必须是原文"写在提示词里只是希望模型做到，写在 `check_finish` 里才能保证做到。
- **字面检索的盲区可以变成考点。** BM25 找不到"WFH"，正好用来检验模型会不会改写查询。
- **用例要能区分好坏。** C02 最初用的改写太难，导致 Mock 必然失败。调整后分成两档：中等改写（C02）验证一致性，强改写（C07）验证模型的查询改写能力。
- **真实模型会暴露离线测试发现不了的问题。** 数字校验误伤和 C07 预期过窄，都是第一次接真实模型时才发现的。离线测试保证规则按设计执行，但规则本身合不合理，要用真实输出来检验。
- **先看原文，再归类。** v2.1 剩下的 6 次退回，只看汇总时被归为"句中序号"；逐条看了答案原文才发现，主要是"第 2 条"这类条款引用，以及模型把换行写成了字面的 `\n`。修之前又用全部退回记录回放了一遍新规则，确认"0 天"这类该拦的仍然会被拦下，再花钱重跑。
- **改进要量化，结论要如实写。** v2 的 6 项决策里，"失败 2 次就停"和"追问列出选项"效果明确；"回答精简"只让字数减少约 8%，效果有限。统计时还犯过一次错（筛选条件漏掉了 C12），复算后才得到正确的数字。

## 下一步

0. **把提示词里的软规则变成硬约束**：在代码里限制每轮检索次数，让"最多换 2 次关键词"真正生效（C06 目前几乎每次都多检索一次）。
1. **混合检索**：向量检索 + BM25，提高同义词召回，并对比两种检索下模型改写查询的次数。
2. **冲突评测集**：构造更多"有冲突 / 没冲突 / 有适用范围"的文档对，统计模型冲突判断的准确率和误报率。
3. **多模型对比**：同一组用例分别跑 DeepSeek、通义千问和本地小模型，比较步数、校验被退回的次数和最终状态。
4. **引用定位到字符位置**：引用里带上段落 ID 和字符偏移，方便在界面上高亮原文。
5. **会话持久化和简单界面**：方便非技术用户试用。
